## Confirmed defects

Orca's keyboard dispatcher selects `_presentHandler` during input help instead
of executing a command. The bridge receives several NVDA gestures and invokes
Orca script methods directly, without constructing a native keyboard event.
This bypassed help for Say All, where-am-I/selection/title/status reports,
speech settings, mouse review, browse/focus and structural-mode toggles, the
clock, current-line and focus-shortcut reports, and Elements List. Input help
could change settings, start reading, switch modes or open a dialog. Pass-next
also armed on receipt, letting the following gesture bypass help.

A command received during help could execute after help was turned off but
before its main-loop callback ran. The browse-hook fix in v112 did not cover
these receive-side direct commands.

The final 11 regression methods were run against genuine v112 controller output
generated by main `a4ecd60`. They produced 99 failing assertions across their
subtests, with no errors or skips. The first eight methods produced 95 failing
assertions before the production change.

During validation of the initial fix, a further regression showed that clock
help taps counted toward the first normal clock gesture: it reported the date
instead of the time after help ended locally. The failing test confirmed this
before separating the two tap sequences.

## Fix

Use a keyboard-only command scheduler for the direct script operations and
Elements List. Remember whether help was enabled and which script received the
gesture. If help was enabled on receipt or begins before dispatch, present the
registered native handler's localized description and honor its
`learnModeEnabled` preference. Follow native `_presentHandler` behavior through
the script's presenter; do not invoke the action or retry it after presentation
fails. Structural-navigation help can use the navigation owner's registry.

Commands received during help remain ineligible for execution after help ends.
Help callbacks expire on script changes and shortcut capture; the existing
main-loop scheduler retains session, role, disconnect and handoff guards.
Consumed repeat/release ownership remains unchanged for Insert and CapsLock
gestures. NVDA+1 still toggles help, and fresh commands execute after help ends.

Pass-next received during help only schedules its native description and never
arms receive-side bypass. Help and normal clock gestures have separate tap
sequences, while time/date choices remain fixed when callbacks are queued.
Braille commands retain their existing action path, including panning during
keyboard help.

Advance the generated controller from v112 to v113, recognizing v112 for
upgrade. Root-level Python compatibility wrappers are unchanged. All new
regressions are in the existing Actions `keyboard-and-browse` matrix module;
no matrix inventory changes are needed.

## Limits

Current-line, focused-shortcut, progress-output and Elements List commands have
no exact native handler description in this path. Help suppresses their actions
without announcing an unrelated physical binding. This scheduler does not
synthesize native keyboard echo. Pass-next armed before help begins retains its
existing receive-side delivery contract; this change prevents arming when help
is already enabled. Shortcut capture is checked at callback time; complete
receive-side forwarding to the shortcut editor is outside this fix.

Tests execute generated bridge code with simulated Orca scripts and input.
Loopback uses real TCP framing with a simulated Orca runtime. Live Windows NVDA,
audible speech, physical braille, Linux application acceptance, Xvfb and full
repository discovery were not run. Source and AST checks do not establish live
desktop acceptance.

Existing installations need the normal connect/update flow and an Orca restart
to load the updated controller. No real user configuration was changed. GitHub
Actions were not monitored or awaited, and the PR was not merged.
